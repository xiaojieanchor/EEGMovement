## 目标与开发进度

主线是以第一人称向前行走、后退、左右转向运动想象控制 Quest VR，眼动方向作为辅助，不指定某只手或腿代表方向。REST 必须明确标注；松键、准备、未标注及断流均为 UNKNOWN／拒识。

现有公开仓库包含 Participant 采集端、Hub、ML 服务、Unity 工程、接收端、通信协议、工具与测试。开发记忆还记录了本地持久化、重连补传、公网中继、私有计算服务及训练工作台五区重构。这些是历史实现记录，不能把历史测试及模型成绩当作本机现场验收。

采集电脑只从原厂会话读取数据，先本地保存再主动连接中继，由 Hub 接收、打标和管理。私有计算节点仅由获准 Hub 经 SSH 访问。连接不会自动授权模型或 VR 动作；不恢复旧 NeuraDock 模型、七槽或故障通道规则。

## 1.1.6 修复

旧界面只显示 InUse=true 的设备，将已连接但未建立会话的设备隐藏为“无”。新版显示全部可见 g.Nautilus，并区分未发现、序列号不匹配、会话未建立、多会话待选择和不支持的多设备组。会话存在不等于非独占权限或实际数据已确认。

服务状态改用 Windows 自带 SCM 查询，不依赖 pywin32。服务未安装、未运行、权限不足及查询失败分开报告，只请求查询权限，不启动或停止服务。SDK 路径支持 Client API 根目录、C、x64 子目录和带引号路径。原厂错误码在隔离进程间保留。

新增有超时保护的短时只读流检测。仅尝试加入现存会话，统计样本，不保存或转发原始值，不配置／启动原厂采集，不推理或执行 VR。无样本、权限拒绝、会话改变、释放失败或强制退出不能报告流成功。

## 本机原厂 Demo 建立非独占会话

已静态核对本机安装的图形版 Demo：连接时 openExclusively=false。它与附带的 .NET 控制台示例不同，后者使用 true，不能直接替代。这个结论针对本机已核对版本，其他版本需再核对。

1. 运行 `C:/Program Files/gtec/gNEEDaccess/demo/gNEEDaccessDemo.exe`。
2. 在 Device Explorer 使用服务器 `127.0.0.1`、端口 `50223`，点击 **Find connected devices...**。
3. 选择自己的 g.Nautilus，点击 **Select**。首次建立会话应显示 **Connected** 和 **owner**。
4. 在原厂配置中核对实际通道、采样率；实际 EEG 输入选择 **Electrode**，不要将手册示例的内部测试信号当作 EEG。
5. 在原厂窗口启动采集，确认 **Acquiring...**，保持窗口打开。
6. 回到新版 EEGMovement，点击“发现本机EEG设备”，再开始接收，或先运行下面的流检测。

其他原厂程序需使用其支持的非独占设置或在连接代码中设置 openExclusively=false；并非每个界面都有复选框。修改后通常需由原厂程序重新建立会话。EEGMovement 不接管独占会话。

## 在源码目录运行

先按[Windows 开发指南](另一台Windows开发指南.md)准备依赖。PowerShell 在仓库根目录运行：

```powershell
# 检查 SDK、GDS、设备及会话，不读取样本或访问中枢
.\.venv\Scripts\python.exe -m gnautilus_acquisition --diagnose

# 原厂已经开始采集后，短时验证真实 Participant 样本
.\.venv\Scripts\python.exe -m gnautilus_acquisition --diagnose --probe-stream --probe-seconds 2

# 多设备时明确选择 SDK 返回的真实序列号
.\.venv\Scripts\python.exe -m gnautilus_acquisition --diagnose --serial YOUR_DEVICE_SERIAL --probe-stream

# 报告仅本地保存，outputs 不进入 Git
New-Item -ItemType Directory -Force outputs | Out-Null
.\.venv\Scripts\python.exe -m gnautilus_acquisition --diagnose --report-path outputs/device-diagnosis.json

# 启动源码工作台，也可双击 scripts/start_acquisition.cmd
.\.venv\Scripts\python.exe -m gnautilus_acquisition
```

退出码 0 表示本次检查条件满足；2 表示未就绪或诊断错误。未加 --probe-stream 时，0 仅代表发现可尝试加入的单设备会话，stream_verified 仍为 false。只有显式读取并收到样本才可能为 true；hardware_verified 保留 false，因为该命令不能验收电极质量或识别效果。

SDK 不在标准位置时加 --sdk-dir "实际 Client API 路径"。命令行本机检测独立于中枢注册和公网，可分别定位硬件层与网络层。

旧安装版不会因 git pull 自动替换；开发时用源码入口或重新构建。旧 1.1.5 快捷方式可能继续运行旧版。原厂 SDK／手册、EEG、权重、密钥、运行身份和缓存仍保存在本机，不随公开源码上传。

## 1.1.7：原厂已开始采集后的实机兼容修复

用户在原厂 Demo 启动采集后，Participant 连接、实际配置、支持采样率、可用通道和 GetDataInfo 均通过。但 GDS_GNAUTILUS_GetScaling 返回 0xFFFFFFFF 与原厂原文 Data acquisition is running.，阻断了原来的启动过程。另行实测滤波目录和设备信息查询可用，问题集中在运行中校准缩放参数查询。

缩放参数仅用于诊断元数据，本程序不使用它重新缩放 GetData 浮点样本。现在仅对上述原厂错误码与明确消息的组合，将 scaling 记为 null，并在 scaling_query 中保留 unavailable_during_acquisition、原厂码和未执行客户端缩放的信息；不停止原厂采集，也不填入默认系数。其他缩放查询错误仍拒绝继续，会话变化仍中止，通道／采样率／输入源／宽度检查全部保留。

现场源码检测在约 3 秒内收到 752 个扫描、94 个块，原厂配置为 250 Hz，32 路 EEG，加 LINK（%）和 DIGITAL（bits）共 34 列。配置输入源为 Electrode；完整 stream descriptor 通过合同校验，参与者正常释放且 close_errors 为空。实际位置接线仍未确认，校准元数据在运行中不可查询，接触质量及识别效果未验收；本次检测没有保存或转发原始 EEG。

本轮相关回归共 127 项通过，新增覆盖运行中缩放查询的明确拒绝、未知元数据、原始值不变、其他错误仍拒绝以及查询期间配置变化的中止。源码及新版便携包以 1.1.7 为准，旧 1.1.6 尚不包含此实机修复。

最终 1.1.7 Windows EXE 也完成了现场短时取数：约 3 秒收到 752 个扫描、94 个块，stream_verified=true；与源码结果一致。打包后的导入、错误诊断、离屏界面及只读审计检查通过。原厂会话保持由原厂控制，未保存或公开原始 EEG。
