# 热点直连连续性与打标修复（1.1.13）

## 现场现象与原因

2026-10-24 现场快照显示，热点输入年龄约 40–60ms，但约 1.5 秒内中枢的 `source_epoch` 从 730 增至 738，连续窗口反复缩短到 8–96 个样本。主动打标因 `source_changed` 中断。这是数据连续性重置，不是网页刷新或 32 通道布局改变。

检查原始块提交日志后，发现实时到达序号存在 5311→5314→5320→5323 等跳跃，被跳过的块之后以补传到达。没有据此断言原厂设备真的漏采样。

直接原因：

1. 1.1.12 热点发送器每轮选择当前最大块号，尚未发送的中间块不走实时通路。中枢正确检测到实时序列缺口，随后重置窗口并结束标签会话。
2. 同一线程发送后逐块等待确认。确认、状态或打标回包稍有延迟，下轮就更容易跨过多个新块。
3. 公网连接在后台断开或重连时，无条件通知中枢数据源失联；这会影响已经独立通过热点工作的采集会话。

## 修改

- 热点发送端按已提交块号递增扫描，优先发送最早尚未发送的新鲜块，停止“只发最新块”。扫描每次最多检查 64 个候选，避免长记录全量扫描。
- 接收确认使用独立线程，发送线程不再逐块等待一次网络往返；未确认数据最多 8 块，历史补传最多占用 2 个并发位置。超时保留本地记录，关闭连接后重连。
- 历史块仍标为 `backfill`，不会进入实时推理；发送前过期的新鲜候选转为后续补传，不重新赋予当前时间。
- 状态、打标确认和数据确认由同一接收线程区分，保留客户端原有事件序号、保存和确认逻辑。
- 中枢登记当前实际输入路径。当前路径是 `lan_ws` 时，公网连接变化仍停止公网动作，但不重置热点输入或关闭热点标签会话。
- 状态接口及采集端反馈增加 `active_transport`、`gap_count`、`last_gap`；断点记录上一个／当前块号、预期／当前样本起点、计数器异常、时间和传输路径。
- 发布版本统一为 1.1.13，签名清单序号 11013。保留原页面与采集端布局。

250ms 实时数据新鲜度、真实缺口重置、UNKNOWN、独立手动启动推理／动作和失联停止规则保持。未配置原厂滤波或启停原厂设备；未修改电极映射。

## 验证及边界

新增测试首先复现两个失败：批量连续块只发最新块且等待确认、公网重连错误通知热点输入失联。修改后通过，并验证 8 块并发上限和历史数据隔离。最终相关回归 63 项通过，覆盖公网及热点合成链路、主动打标与保存、32 通道软件闭环、时钟和过期数据拒绝。

本机中枢已重启加载修复。采集程序已生成 1.1.13 安装器与便携 ZIP，完成冻结启动、Qt 离屏界面、证书环境和只读日志核验；不是原厂 SDK 或设备实机验收。

现场最后运行的是旧版 1.1.12；中枢重启后尚未收到新版真实数据。因此未宣称连续记录、打标或识别效果已经实机通过。

## 采集电脑更新与现场核验

结束自主打标，结束接收并保存后，安装 1.1.13；保留原厂采集会话和已有数据目录。再选择热点直连，开始接收。源码开发环境可拉取同一修复提交后重启采集端。

公网 SSH／TLS 目前不可达，不能将本次安装包写成“已推送公网自动更新”。已提供本地安装包，并通过项目 GitHub 发布渠道交付；公网恢复后可用原签名发布流程同步同一不可变安装包。

持续接收至少 5 分钟，确认块号及样本位置递增；`gap_count` 不再因软件跳块或公网重连增长。依次记录按住、松开、方向切换和停止，核对本地与中枢事件及保存样本数。松开后的区间应为 UNKNOWN，不能补为 REST。

再测试短时网络抖动、真实断开和重新连接。真正过期或断流时仍应停止实时执行、结束受影响标签区间；恢复后重新手动开始标签会话。不能以维持界面“绿色”替代真实连续性。
